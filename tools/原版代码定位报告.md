## 1. 玩家位置读取（PlayerMoudle / `_gPlayer`）

**模块**：`PlayerMoudle`（模块段起始 @1703950，类名 `PlayerMoudle`，导出单例属性 `i._gPlayer`）。模块内 `_gPlayer` 全局可见，全文件大量跨模块以 `_gPlayer` 读写。

**位置字段**（构造器 @1705279-1705555）：
```js
this.playerPos=cc.v2(500,500); this.posSceneType=0; this.sceneType=0;
this.timeNode=0; this.time=0; this.day=0; ... this.playerPlace=f.PlaceType.NORMAL;
```

**核心读取函数**（同一个模块 @1708512-1708680）：
```js
// getPlayerPosition(): 场景一致才返回真实 pos，否则给默认点(500,500)
getPlayerPosition(){return this.posSceneType==this.sceneType?this.playerPos:cc.v2(500,500)}
// updatePlayerPosition(): 从 Application.playerNode 快照当前坐标，并记录对应场景
updatePlayerPosition(){this.playerPos=Application.getIns().playerNode.getPosition(); this.posSceneType=this.sceneType}
// getSceneType(): 当前所在 SceneType
getSceneType(){return this.sceneType}
```
- 玩家运行时坐标存放在 `global/Application` 单例的 `.playerNode`（Node）。任何代码要读"玩家在哪"都走：`_gPlayer.getSceneType()` 拿场景 + `_gPlayer.getPlayerPosition()`（或直接 `Application.getIns().playerNode.getPosition()`）拿坐标。
- 存档结构 `playerPos:[x,y]` + `posSceneType` + `sceneType`（见 `villagedb.qt` 的 `playerData_100001`）。
- `getPlayerPlace()`/`changePlayerPlace(e)`（@1714840-1715028）：NORMAL=1 / HOT_SPRING=2（`PlaceType`，GameDefine @354078），热泉/温泉时改外观（`PlayerItem.updateFigure()`）。
- 场景变更：`chaneScene(e)` @1708505（代码里拼写为 `chaneScene`）——置 `sceneType=e` 并 `fire(GAME_EVENT.CHANGE_SCENE)`。

> **多人联机注入点**：`getPlayerPosition()` 是其它玩家要查询本机玩家的权威读取口；`updatePlayerPosition()` 是位置快照点（sceneType→posSceneType 绑定）。跨端同步请求位置时优先用这两者 + `Application.playerNode`。

## 3. NPC 系统

### 3a. NPC 配置来源（26 个 npcId）
- 配置表模块 **`Gnpc_config`**（模块段 @637471），内容与 `D:\agent社区\AgentFarm\data\npcs.json` 一一对应。单条：`o.set(id,{path_name,appear_rule,talks,over_talks,nameId,id,sex_clothes,animal_id,scale,hs_talk_id,head,appear_1,appear_2,path,poses,first_talk_id,gender,notes,give_props,...})`。例 npc1 `{path_name:"jiashibo",head:"dtu_gjsb",gender:1,scale:1,notes:"家石伯",appear_rule:[[2,10101,2,5566,5110],...],appear_1:[[2,.5],[103,.5]],appear_2:[[103,1]],...}`。
  - **名字/外观**：`nameId`(→`_gLang1` 文字)、`head`(头像)、`path`/`path_name`(骨骼/贴图路径)、`gender`(1男/2女)、`scale`。
  - **所在场景/时段**：`appear_rule`（任务/条件型）、`appear_1/appear_2`（按 TimeNode 的概率场景表）。
  - **是否可交易(shopId)**：`Gnpc_config` **没有 shopId 字段**。交易入口在 `NpcMoudle.onBtnShop/onBtnSell` @1598514/@1599031 → `openUi({uiRes:UI_SHOP, data:ShopType.BUY/SELL})`；店铺商品表是独立 `Gshop_config`（@724093）。NPC 关联商店系通过其所在场景/交互按钮，而非配置字段。
- 运行时 NPC 实例类 **`Npc`**（模块段 @1603659）：`init(e)` @1604059 读 `{stayScene,npcId,lastTalkingDay,originTalkingDay,starNum,stayPos,talkIdx,giveProps,placeType,constDir}`；`getData()` @1604258 序列化回存。**NPC 由 `NpcMoudle` 通过 `Gnpc_config.values()` 全量创建**（`loadData` @1582611：`createNpc(a.npcId,a)`，缺失的用配置补 `createNpc(l.id)`）。

### 3b. NPC 对话窗口 / 台词来源
- **对话打开入口**：`NpcMoudle.talkToNpc(npcId)` @1586651：读该 NPC `placeType`；HOT_SPRING 用 `hs_talk_id`/`hs_full_talk_id`；否则先 `TaskMoudle.getTaskTalk(npcId)`（任务驱动优先），再遍历 `cfg.taskWords`（[1]已接→push、[2]可接→push），仍空则 `npc.getTalkId()`；随后 `onTalk(npcId)` 记录对话日，`openUi({uiRes:GameRes.UI_TALK, data:{words:[...], isAllowClose:!0}})` @1587321。
- **台词查取** `Npc.getTalkId()` @1606962：未开口且 `first_talk_id>0`→首句；`starNum>=3&&over_talks.length>0`→`over_talks`；BAO_LONG 过任务→`over_talks`；否则 `talks[this.talkIdx++]`（轮询，越界归 0）——**这就是按 (npcId, talkIdx) 取台词的核心**。中文字串经 `ConfigureHelper.getWordParam(npcId,talkId)` 取 `_gWord[talkId]`；多句脚本走 `getTalkParamByGroup(groupId)`。
- **歌词组装**：`NpcMoudle` 用 `ConfigureHelper` 生成：`ConfigureHelper.getTalkParam([talkGroup],true)`、`getWordParam(npcId,talkId)`、任务对话 `TaskMoudle.getTaskTalk(npcId)` @1586920-1587210。
- **ConfigureHelper**（模块段 @195820）核心：
```js

getTalkParam(e,t=!0){var o={words:[],isAllowClose:t,cb:i}; for(...) o.words.push(this.getWordParam(s[0],s[1])); return o}

```
- **台词表 Language / `_gWord`**（模块 @1321620）：把全部 `Gwords_*` 配置 `Map` 合并成 `_gWord`（键=talkId，值 `{str,face,japanese,traditional,english}`）；`_gLang1`（键文本 id）。语言切换 `updateLanguage(langType)` 从 `str/traditional/english/japanese` 选字段。**NPC 台词 = 按 talkId 查 `_gWord`**，命中即一段话 + `face`（表情）+ `voice`(音频)。
- **对话窗口渲染**：`UiTalk`（模块段 @2148612，`initNode` @2150784 取 `centerDown/pnlTalk/rtTalk` cc.RichText、`pnlName/lbName`、`spFigure` Skeleton、`imgTipsNode`）。`initData()→startTalk()→nextTalk()` @2151033-2151512：`this.talkIdx++`，读 `talkParam.words[talkIdx]`，做 `o.str.replace(nameRegexp,"<color=#FF7F00>"+playerNick+"</color>")`，播 `o.voice`；`talkEnd()→closeUi()`（回调 `talkParam.cb`）。
  - **拦截点**：`openUi(UI_TALK,data:{words})` 的 `data.words` 就是给 UI 的对象。做 LLM 对话 = 替换 `ConfigureHelper.getTalkParam/getWordParam` 返回值，或直接改写 `data.words` 为 `ConfigureHelper.getWordParamByStr(npcId,["<LLM文本>"],face)`。

### 3d. NPC 日常行为（走动/日程）

## 4. 存档 key 全集（localStorage / .qt）

**层级**：
- **StorageUtil**（模块 @1975129，纯 localStorage 工具）：`getItem/setItem/getNum/removeItem/getObj(JSON.parse)/setObj(JSON.stringify)`。
- **SdkManager → 由 `NativeApi`（@1527861，app 真机）或 `WebApi`（@2203240，Electron 本 build 生效）实现**。`getStorageObj(key,def)`/`setStorageObj(key,obj)` 对本机内存 `storageData` Map 深拷贝读写；`saveStorageData()` 整文件全量落盘。在 `PlayerMoudle` 里 `n=SdkManager`，故 `n.getStorageObj(storageKey,{})`。
- **持久化落盘**（.qt + localStorage 双写）：
  - `WebApi`（本 build）：`login` → electron `getUserId`（@2204353）取 uid → `storageFileName="villagedb_"+uid`（@2204634）→ `loadStorageData`：`StorageUtil.getObj(fileName,{})` + `loadData(fileName+".qt")` 取 **version 高者**（@2204870）灌入内存 `storageData` Map；`getData()`（@2205831）组 `{version,datas:[{key,val}]}`；`saveStorageData()`：`storageVersion++` → `h.saveData(fileName+".qt",JSON)` → `StorageUtil.setItem(fileName,JSON)`（异常则 `localStorage.clear()` 重试）。
  - `NativeApi`（真机）：`login` 后读写 `h_storage/1000001_normal[_binary].qt`；`startSchedule()`（@1529576）`setInterval(function(){},100)` 为**空占位，不持久化**。
- **GameManager.saveData()** @357967 = `_gPlayer.saveData()` + `GameData.saveData()` + `SdkManager.saveStorageData()`（非 SceneManager/DataManager——全文件无 `SceneManager.prototype.saveData`，无 `DataManager` 模块）。
- **统一登录加载入口** `GameScene.loginSdk` @369166：`SdkManager.login(→loadStorageData) → GameData.loadData() → AudioManager.init → ModManager.init → GameManager.startGame(storageKey)` → `_gPlayer.init(storageKey)`。

**"频繁写"结论**：文件持久化 `saveStorageData()` 仅由 `GameManager.saveData()` 触发（@358040，全文件仅 4 处**集中调用点**：日/夜切换回调@1710722/@1711217、UiMain 按钮@2063228、批量/剧情处）。**无逐帧、无定时器写盘**——`PlayerMoudle.updateTime`（@1712495）逐 tick 只 `time+=1` 发 CHANGE_TIME，`updatePlayerPosition`（@1708585）只存内存快照；位置/时间只有在 `saveData` 时（昼夜切换/剧情/设置）才落盘。

> **多人联机注入点**：需要**服务器同步**——`playerData`（位置/时间/天气）、`mapData`/`plantData`/`farmData`（建筑/作物）、`npcData`（好感/NPC位置/产奶）、`taskData`/`achvData`（任务/成就）、`knapData`（背包）、`shopData`/`makeData`/`castingData`/`attributeData`/`plotData`。建议只客户端——`audioData`、`settingData`（moveType/性向显示）、`gameData`（语言/CV）。持久化是**整文件全量写**（WebApi `saveStorageData` 写整个 `.qt`+localStorage），改造应把各 key 拆成服务器字段、在 `GameManager.saveData` 处 diff/增量同步，复用 `storageVersion++` 作冲突检测/最后写入者。位置高频同步不要依赖存档（无逐帧写），走 §9 的 `RoleStateMove.updateMove`。

- `WeatherType={NONE:0,SUNNY:1,RAINY:2}`（GameDefine @352399）。`getWeatherType/setWeatherType/updateWeatherType` @1714228-1714350：MORNNING 20–25% 概率置 RAINY。

> **多人联机注入点**：`onChangeTimeNode`（@1712187）与 `updateTime` 广播 `GAME_EVENT.CHANGE_TIME(NODE)` 是客户端推进点；跨端需统一基准（time 是本地 500ms/分钟 轴，不在线同步会漂移）。建议用某端为时钟源，其它端只读。

## 9. 移动控制（键盘 / moveType）

**输入 = 纯键盘**（非摇杆）。`PlayerJoysticks`（@1699841，挂载于 PlayerItem，`onLoad` @1701315）：
- `onEventStart` @1701523：`cc.systemEvent.on(KEY_DOWN/KEY_UP)`；监听 WASD + 方向键。

**moveType（settingData.moveType）不是"输入方案"，而是 走/跑 速度模式**：
- `MoveType={NORMAL:1, RUN:2}`（RoleDefine @1775553）。`settingData.moveType=2`=RUN（见 `.qt`）。
- 读取：`SettingMoudle.getMoveType()` + `SettingMoudle.loadData` @1857603 读 `settingData`；`changeMoveType` @1858025 循环切换 NORMAL↔RUN（体力不足弹 `_gLang1[318]`），成功后 `fire(GAME_EVENT.CHANGE_MOVE_TYPE)` 并 `PlayerItem.setMoveType`。
- 速度：`PlayerItem.getSpeed()` → `moveType==NORMAL?250:500`；`RoleStateMove.updateSpeed(e)`（HOT_SPRING 时 600）。
- UI 绑定：UiMain HUD `onBtnMoveType` @2064677 + UiMgr `shift` 键；`UiSetting` 面板本身不读写 moveType。

**移动执行链 / 位置权威写点**：
键盘→`PlayerJoysticks.checkDir`→`PlayerItem.changeDir(dir,doublePress)`(@1696830，定 moveDir / 决定 NORMAL/RUN / `intoState(MOVE)`)→`PlayerItem.intoState+`→`RoleStateMove`(@1794696)：
```js
onEnter(e,t){this.targetPos=e; this.updateSpeed(t); this.updateMoveDir(); this.updateMoveVector(); this.startHandle()}
updateMove(e){if(this.view.getMoveDir()!=INVAIL){let p=this.view.node.getPosition();
  this.view.node.setPosition(p.add(this.moveVector.mul(this.speed*e))); this.fixPosition();
  this.view.node.getComponent(cc.RigidBody).syncPosition(!0)}}
```
  —— `updateMove` @1797698 是**唯一每个渲染帧改变玩家 node 坐标**的地方（`speed=250/500`，方向 `moveVector`）。`PlayerMoudle.updatePlayerPosition` 只是快照。

> **多人联机注入点**：实时位置同步应在 `RoleStateMove.updateMove` 的 `node.setPosition` 处收发（或节流批量）；要移动“其它玩家”角色可挂同样 `PlayerItem+PlayerJoysticks(RoleStateMove)`，用服务端坐标 setPosition。

# 对多人联机改造最重要的 5 个注入点（按重要性排序）

1. **位置权威写点 `RoleStateMove.updateMove` 的 `node.setPosition`（@1797698）+ 快照 `PlayerMoudle.updatePlayerPosition`（@1708622）** — 每帧改变玩家 / 其它玩家坐标的唯一处。联机一切"谁在哪"都经它；其它玩家渲染 = 复用 `PlayerItem`+`cc.instantiate(prefab_player)`（@358479）按服务器坐标驱动。没有它，跨端位置就是每 9 分钟才停一次的存档快照，无法实时。

2. **`UiMgr.openUi/@2086285` + `GameRes`(ResDefine @1750876) 面板注册机制** — 多人的聊天窗口、玩家列表、组队、状态栏面板全靠这套 openUi/popUi 生命周期挂到 uiLayer；新 UI 与主 HUD(UiMain) 的集成成本最低。输入直接用现成 `cc.EditBox`（仿 UiRename @2114407）。

3. **存档/读写层 `StorageUtil`+`SdkManager.get/setStorageObj` + key 拼接 `getStorageKey`（PlayerMoudle @1708666）** — 所有需要同步的共享状态（位置/时间/天气、NPC 好感、任务、剧情）都落在 `xxxData_<uid>` key 里，统一在这里做"写成员时才同步"的旁路最干净；服务器需同步哪些 key、哪些留本地（settingData/audioData/gameData）由此界定。

4. **时间轴与广播 `PlayerMoudle` 的 `startTimeSchedule/updateTime/setTimeNode/onChangeTimeNode`（约@1709694-1712660）** — 权威时钟在这，昼夜/天气/NPC 行为都随 TimeNode 步进。多人需统一游戏时钟（本地 500ms/分钟轴会漂），在此做时钟源/推进广播 + `CHANGE_TIME(NODE)` 事件转发是正确层级。

5. **NPC 对话侧 `ConfigureHelper.getTalkParam/getWordParam/getWordParamByStr`（@195820）+ `NpcMoudle` 对 `UiTalk.openUi(UI_TALK,data)`（@1587321）+ `addStarNum`（@1606762）** — 原生台词到 LLM 对话、NPC 好感/NPC 位置的跨端一致、对话窗口拦截三个"社交内容"需求全在这条 配置→组→词→UI 的链路里解决，是最贴近"让原版 NPC 变成可互动多人角色"的业务注入面。

> 附注：未定位到 `changeSceneHard`（全文件 0 匹配）；`Gnpc_config` 无 `shopId` 字段（商店经 `Gshop_config`+UI_SHOP 独立管理）；未发现现成聊天消息 UI 与已有多人业务代码（`NetSocket`/`WebMsgHandler` 是基础设施，需另行确认职责）。
